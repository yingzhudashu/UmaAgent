# 会话与执行能力审查记录（2026-09-21）

## 结论

本轮问题集中在同一个根因：消息树、活动分支、质量派生结果和执行队列没有共享一套可验证的对象版本。不应继续在现有 `conversation_branch_forks` 查询条件上叠加例外；需要一次性迁移到明确的替代关系、分支版本和队列版本。

## 本轮已修复

- 活动历史按当前 head 的父链和明确公共前缀读取；无关的全局 sequence 消息不再自动混入。
- 编辑只允许当前活动路径上的已完成用户消息；编辑分支继续使用被编辑消息的直接父消息。
- 审查和改进结果不再混入普通会话正文；质量接口返回改进结果正文，重置改进只沿改进结果链回溯。
- 排队消息编辑同步更新用户 payload，执行时不会继续使用旧文本。
- 运行控制器按 `runId` 隔离；抢占覆盖等待输入/确认状态，会话级取消优先取消 Agent/command，不误取消质量运行。

## 已确认的实现缺口

### 会话和编辑重跑

1. 编辑仍只写入现有 fork 表，没有记录替代消息、源分支和分支版本；连续编辑、刷新、分页和旧回执仍缺少统一版本门禁。
2. 活动分支没有持久 `branchRevision`；历史分页在编辑并发发生时只能通过客户端主动丢弃游标恢复。

### 队列、抢占和切换

1. 队列排序只提交 Run ID 列表，没有持久的 `queueRevision`；服务端无法向客户端说明排序基于哪一版快照。
2. `RunOrchestrator` 的内存队列与数据库队列分别维护。进程恢复、排序和抢占期间存在短暂不同步窗口，缺少统一的队列事件版本。
3. 抢占结果还没有统一持久的 superseded 原因字段；当前通过 cancelled/interrupted 和错误文本表达，客户端难以区分“用户取消”和“被新消息替代”。
5. 质量 Run 和 Agent Run 共用会话队列但没有统一的优先级与抢占规则，用户无法预测“审查/改进”何时执行。
6. `listQueue` 用当前数据库排序重新计算位置，客户端不能区分“位置改变”和“对象已被取消/开始执行”，迟到回执容易复写旧列表。

## 实施顺序

1. **协议与数据库**：新增 branch revision、替代关系、quality target revision、queue revision/order 和明确的 Run superseded 原因；schema 26→27 一次性迁移，迁移前备份，无法唯一推断的记录停止迁移并报告。
2. **Core**：用父链公共前缀计算活动路径；编辑/重跑原子创建 replacement；质量操作默认只写质量表；控制器改为 runId；队列由持久快照驱动并在同一事务发布版本事件。
3. **Server/Client**：所有写请求携带对象版本；过期写返回冲突和最新快照；Web/Android 只按账号、会话、branchRevision、queueRevision 和对象 ID合并回执。
4. **测试与验收**：先补 Core 事务测试，再补 Server 契约测试、Web/Android 投影测试和真实设备流程；未完成矩阵不得发布。

## 发布门槛

- 编辑根消息、中间消息、末尾消息和连续编辑后，普通历史只显示活动路径。
- 重跑覆盖当前结果；旧路径可审计但不混入当前正文。
- 审查不产生普通正文；改进未采用不改变上下文；采用操作可追溯。
- queue 模式排序、编辑、取消、冲突和恢复可重复；preemptive 模式对 queued、running、暂停、只读动作和副作用动作有明确结果。
- 切换会话、账号、后台恢复、断线重连和迟到事件不会污染当前会话。
- 数据库迁移、完整性检查、协议校验和 Web/Android 端到端验收全部通过。
